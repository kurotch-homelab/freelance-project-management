# フリーランス案件管理システム 要件定義

フリーランス本人が自分の案件・契約・稼働・請求見込み・稼働予測をまとめて見られる Web アプリの要件をまとめる。
開発は TDD で進める。3 章の「例」の表は、そのまま最初の Vitest テストケースにする。

## 1. 目的とスコープ

- 利用者: フリーランス本人 1 人だけ
- 形態: Web アプリ。自宅サーバーの Docker か Kubernetes で動かす
- 認証: OIDC でログインするだけ。権限管理はしない(パスワードを持たないのが目的)

### MVP に入れるもの

- 取引先・案件の管理(ステータス: 提案中 → 受注 → 稼働中 → 完了 / 失注)
- 契約・単価の管理(準委任・時間単価のみ)
- solidtime から稼働時間を取り込んで、案件ごと・月ごとに集計
- 請求見込み額の計算(税抜・消費税・税込)
- 請求書の作成ガイド: freee で請求書を作るときに入力する内容(品目・数量・単価・金額・請求日・支払期日など)を、取引先 × 月ごとに表示する
- Google Drive に案件フォルダを作り、契約書・請求書 PDF を保管(請求書 PDF は freee から落としたものを手でアップロード)
- 稼働時間予測を案件ごとに自動で作る(solidtime の過去実績 + Google Calendar の Out of Office)
  - 今月の着地見込み(実績 + 残り日数の予測、請求見込み額も出す)
  - 来月以降数か月の月ごとの予測時間と売上見込み
  - 日ごとの予定(「この日は案件 A を 4h」)

### MVP に入れないもの

- 月額+精算幅、請負・固定額の契約(時間単価契約の「月の目安時間」は MVP に入れる)
- 源泉徴収の計算
- freee との API 連携(請求書の作成・取得、入金状況の取得)。請求・会計の作業は freee を自分で操作する
- 複数ユーザー、権限管理

### 将来の候補

- 請求済み・入金済みを手でチェックして、未入金の一覧を出す
- freee 連携(必要になったら)
- 稼働報告書の出力
- 月額+精算幅の契約

## 2. ドメインモデル

| エンティティ | 主な項目 |
|---|---|
| 取引先 Client | 名前、締め日、支払サイト(例: 月末締め翌月末払い)、請求書の件名テンプレート、solidtime client ID、Drive フォルダ ID |
| 案件 Project | 取引先、名前、ステータス、期間、solidtime project ID、Drive フォルダ ID |
| 契約 Contract | 案件、契約期間、単価履歴(適用開始日つき)、月の目安時間(下限 / 上限、どちらも任意) |
| 月の目安時間の上書き HoursRangeOverride | 契約 × 対象月。その月だけの下限 / 上限、合意のメモ、記録日 |
| 稼働 TimeEntry | solidtime から取り込んだ打刻と集計値。開始・終了・時間、billable フラグ、solidtime entry ID |
| 請求見込み BillingEstimate | 案件 × 対象月。稼働時間合計、税抜額、消費税、税込額 |
| 請求書ガイド InvoiceGuide | 取引先 × 対象月。請求日、支払期日、件名、明細行(品目・数量・単価・金額)、税抜・消費税・税込。保存はせず、その都度計算する |
| 不在予定 Absence | Google Calendar の Out of Office から取り込む。開始・終了日時、calendar event ID |
| 稼働予測 Forecast | 案件 × 日付。予測時間、予測のもと(案件の実績 / 同じ取引先の実績 / 稼働の空き)、参照した週数、作成日時 |

## 3. 計算ルール(最初の TDD 対象)

- 稼働時間: solidtime の集計値をそのまま使う。日や月をまたぐ打刻は solidtime が開始日の側に入れるので、このシステムでは分けない。billable な打刻だけを対象にする
- 請求時間: 稼働時間(h)を小数第二位で切り捨てる(例: 10 時間 1 分 = 10.0166…h → 10.01h)。請求書の数量もこの値にする
- 金額: 請求時間 × 時間単価。円未満は切り捨て
- 消費税: 請求書合計(税抜) × 10%、円未満切り捨て。請求書ごとに 1 回だけ端数を処理する
- 単価が月の途中で変わったら、単価ごとに請求時間と金額を出す(請求書の明細行も分ける)
- 入金予定日: 対象月と取引先の締め日・支払サイトから出す

### 例(そのままテストケースにする)

| ケース | 入力 | 期待値 |
|---|---|---|
| 基本 | 5,000 円/h、合計 37 時間 15 分 | 税抜 186,250 円、税 18,625 円、税込 204,875 円 |
| 割り切れない時間 | 5,000 円/h、合計 10 時間 1 分 | 請求時間 10.01h、税抜 50,050 円、税 5,005 円、税込 55,055 円 |
| 円未満が出る | 4,850 円/h、合計 10 時間 1 分 | 10.01h × 4,850 = 48,548.5 → 税抜 48,548 円 |
| 稼働ゼロ | 打刻なし | 0 円。請求見込みは「対象なし」として作る |
| billable=false | 2h のうち 30 分が non-billable | 1.5h 分だけ計算 |
| 単価変更 | 15 日まで 5,000 円で 20h、16 日から 6,000 円で 10h | 100,000 円 + 60,000 円 = 税抜 160,000 円 |
| 月をまたぐ打刻 | 11/30 23:00〜12/1 01:00 | solidtime の集計どおり 11 月に 2h(アダプターのテストで確かめる) |
| 入金予定日 | 月末締め翌月末払い、11 月分 | 12 月 31 日 |

### 請求書の作成ガイド

freee で請求書を作るときに、そのまま入力できる内容を取引先 × 月ごとに出す。各項目にコピーボタンをつける。

- まとめ方: 同じ取引先の案件は 1 枚の請求書にまとめ、案件ごとに明細行を分ける
- 明細行: 品目 = 「案件名 YYYY年M月分」、数量 = 請求時間(小数第二位まで)、単位 = 時間、単価 = 時間単価、金額 = 数量 × 単価(円未満切り捨て)
- 月の途中で単価が変わった案件は、単価ごとに明細行を分ける
- 数量は小数第二位で切り捨てるので、freee で「数量 × 単価」を計算させても金額が一致する
- 請求日: 取引先の締め日。支払期日: 入金予定日
- 件名: 取引先ごとのテンプレート(例: 「{YYYY}年{M}月分 業務委託料」)
- 合計: 税抜合計、消費税(請求書合計で 1 回切り捨て)、税込合計。freee の画面に出る金額と見比べられるようにする
- 稼働ゼロの案件は明細に出さない。全案件がゼロなら「請求なし」と出す

| ケース | 入力 | 期待値 |
|---|---|---|
| 1 案件 | A 社・案件 X、11 月 37 時間 15 分、5,000 円/h、月末締め翌月末払い | 品目「案件 X 2026年11月分」、数量 37.25、単価 5,000、金額 186,250。請求日 11/30、支払期日 12/31。税 18,625、税込 204,875 |
| 2 案件をまとめる | A 社の案件 X 186,250 円、案件 Y 50,000 円 | 明細 2 行、税抜 236,250、税 23,625、税込 259,875 |
| 単価変更 | 案件 X、15 日まで 5,000 円で 20h、16 日から 6,000 円で 10h | 明細 2 行(100,000 円 / 60,000 円) |
| 割り切れない時間 | 10 時間 1 分、5,000 円/h | 数量 10.01、金額 50,050 |
| 稼働ゼロ | 打刻なし | 「請求なし」 |

### 月の目安時間(下限・上限)

- 契約に月の下限・上限を持てる(片方だけ、なしも可)。多くは相談で変えられる目安として扱う
- 請求額には影響しない。請求は常に「実績時間 × 単価」
- 相談して変えたときは、その月だけの上書きとして記録する(合意のメモつき)。上書きがあればそれを優先する
- 使い道は警告: 今月の着地見込みや来月以降の予測が下限を下回りそう / 上限を超えそうなとき、案件一覧とダッシュボードに出す。早めに相談できるよう、何時間足りない / 多いかも出す
- 今月の実績がすでに上限を超えたときも警告を出す

| ケース | 入力 | 期待値 |
|---|---|---|
| 範囲内 | 下限 140h・上限 180h、着地見込み 160h | 警告なし |
| 下限割れの見込み | 下限 140h、着地見込み 120h | 「下限まで 20h 不足の見込み」 |
| 上限超えの見込み | 上限 180h、着地見込み 195h | 「上限を 15h 超える見込み」 |
| 上限超えの実績 | 上限 180h、今月の実績 182h | 「上限を 2h 超過」 |
| 月の上書き | 契約の上限 180h、12 月だけ 200h に上書き、12 月の着地見込み 195h | 警告なし |
| 請求額は変わらない | 下限 140h、実績 120h、5,000 円/h | 税抜 600,000 円 |
| 幅の設定なし | 下限・上限なし | 警告なし |

### 稼働時間予測のルール

- 稼働できる日: Google Calendar に Out of Office が入っていない日はすべて稼働できる日とする。祝日・平日・土日で区別しない。休みたい日は自分で Out of Office を入れる
- 勤務時間帯は決めない(フルフレックスのため)
- 基準: 直近 N 週(初期値 8 週)の曜日ごとの平均稼働時間。曜日ごとの平均なので、普段働かない曜日は自然に 0h になる
- 予測のもとは次の順に選ぶ
  1. その案件の実績
  2. 案件の実績がない場合: 同じ取引先の全案件の実績
  3. 取引先との取引自体が初めての場合: 稼働の空き = 自分の全案件の曜日別平均(1 日に働く時間) − その日のほかの案件の予測。0h 未満にはしない
- 実績が N 週に満たないときは、ある分だけで平均する
- Out of Office: その日の予測時間から不在の時間を差し引く。複数案件がある日は各案件の予測の比率で按分する。0h 未満にはしない
- 契約期間の外の日は 0h
- 今月の着地見込み = 今月の実績 + 今日より後の日の予測。請求見込み額は上の金額ルールで出す
- 来月以降: 日ごとの予測を月で合計する(初期値 3 か月先まで)
- 予測は solidtime / Calendar の同期のたびに作り直す
- N と予測する月数は設定画面で変えられる

### 予測の例(テストケースにする)

| ケース | 入力 | 期待値 |
|---|---|---|
| 曜日別平均 | 直近 8 週の月曜の稼働が案件 A で合計 32h | 次の月曜の予測 4h |
| 祝日も稼働できる日 | 予測日が祝日の月曜、Out of Office なし | 4h(月曜の平均) |
| 普段働かない曜日 | 直近 8 週の土曜の稼働が 0h | 土曜の予測 0h |
| 1 日の不在 | 予測 8h、その日の 0:00〜24:00 が Out of Office | 0h |
| 一部の不在 | 予測 8h、4h の Out of Office | 4h |
| 不在が予測より長い | 予測 3h、5h の Out of Office | 0h |
| 2 案件の按分 | A 6h・B 2h、4h の Out of Office | A 3h・B 1h |
| 実績が少ない | 案件 A の実績が 2 週分だけ、月曜は 5h と 3h | 月曜の予測 4h |
| 同じ取引先の新案件 | 案件 B は実績なし、同じ取引先の案件 A の月曜平均 4h | 案件 B の月曜の予測 4h |
| 初めての取引先 | 全案件の月曜平均 8h、ほかの案件の月曜の予測 5h | 新案件の月曜の予測 3h |
| 空きがない | 全案件の月曜平均 8h、ほかの案件の予測 8h | 新案件 0h |
| 契約期間外 | 契約終了日の翌日 | 0h |
| 着地見込み | 実績 60h、残り日の予測 40h、5,000 円/h | 100h、税抜 500,000 円 |

## 4. 外部連携

すべてポートとアダプターで分け、ドメインは外部サービスを知らない形にする。

### solidtime(セルフホスト)

- 方向: 読み取り(打刻)+ 書き込み(取引先・プロジェクト・単価)
- 単価の正はこのシステムの契約。契約を保存したら solidtime のプロジェクトの billable rate に反映する
- 認証: personal access token(Bearer)。ベース URL・組織 ID・トークンは環境変数(`SOLIDTIME_BASE_URL`、`SOLIDTIME_ORGANIZATION_ID`、`SOLIDTIME_API_TOKEN`)で渡す
- 開発用: LAN 内のインスタンスの検証用組織(Sandbox)を使う。トークンは `.env.local`(git 管理外)に置く
- 参考: solidtime のルート定義 https://github.com/solidtime-io/solidtime/blob/main/routes/api.php
- パスはすべて `/api/v1/organizations/{organization}` の下。集計の時間は秒(`seconds`)、金額 `cost` は通貨の 1/100 で返る
- 打刻の `billable` は自動では決まらない(打刻時に指定する値)。集計では `billable` な打刻だけを対象にする
- OpenAPI 仕様: 公開されている https://api-docs.solidtime.io/api-docs.json を使う(公式ドキュメント https://docs.solidtime.io/api-reference の元データ、OpenAPI 3.1)
  - リポジトリ直下の `openapi.json` は古い(2025-04 更新、4 パスのみ)ので使わない
  - アプリの `/docs/api.json` は本番環境では 403 になる
  - 仕様からアダプターの型を生成し(`openapi-typescript` など)、フィクスチャもこれに合わせる。セルフホストの版と仕様の版がずれていないかは、取り込みのテストで確かめる
- 打刻の取得 `GET /time-entries`: `start` / `end`(UTC)、`project_ids[]`、`client_ids[]`、`billable`(`"true"` / `"false"` の文字列)で絞り込む。`limit` / `offset` でページを送る
- 集計 `GET /time-entries/aggregate`: `group` / `sub_group`、`start` / `end`、`billable` を指定する。`rounding_type` / `rounding_minutes` は指定しない(このシステムでは丸めない)
- 単価の反映: `PUT /projects/{project}` の `billable_rate` に入れる。単位は「通貨の 1/100 / 時間」で、JPY の組織でも同じ。5,000 円/h なら `500000` を送る(2026-11-05 に検証用の組織で確認済み: `billable_rate=500000`、1 時間の打刻で集計の `cost=500000`、CSV 出力では `Amount (JPY) 5000`)。メンバーごとの単価 `PUT /project-members/{projectMember}` の `billable_rate` は使わない
- タイミング: 画面から手動で同期+定期実行(1 日 1 回など)
- 失敗時: 前回取り込み分はそのまま残し、エラーと最終成功日時を画面に出す

### freee

- API 連携はしない。請求書の作成と会計の作業は自分で freee を操作する
- このシステムは「請求書の作成ガイド」(3 章)で入力内容を案内するだけ

### Google Drive

- 方向: 書き込み(フォルダ作成、ファイル保存)+ 読み取り(一覧・リンク)
- 案件ごとに `取引先/案件名/` のフォルダを作り、契約書・発注書・NDA・請求書 PDF を置く。請求書 PDF は freee から落としたものをこのシステムの画面からアップロードする
- 認証: 下の「Google の認証」を参照

### Google Calendar

- 方向: 読み取りのみ
- 自分のカレンダーの Out of Office 予定を、今日から予測期間の終わりまで取得する。`events.list` に `eventTypes=outOfOffice` を指定する
- Out of Office は終日予定ではなく時刻つきの予定として登録される。予定の開始・終了をそのまま不在時間として扱う
- 祝日は扱わない(Out of Office がなければ稼働できる日)
- タイミング: solidtime と同じく手動+定期実行。取得後に稼働予測を作り直す
- 失敗時: 前回取り込んだ不在予定で予測し、画面に「カレンダー未更新」と出す
- 参考: https://developers.google.com/workspace/calendar/api/guides/calendar-status

### Google の認証(Drive・Calendar 共通)

- アカウント: Google Workspace
- 方式: サービスアカウントを使う。渡し方は 2 つから選ぶ
  - Workload Identity Federation(Kubernetes など WIF を使える環境)。サービスアカウントキーは作らない
  - サービスアカウントの JSON キーファイル(WIF を使えない環境)。ファイルのパスを環境変数で指定し、Secret やボリュームで渡す
- どちらも Google の Application Default Credentials の仕組みで読み込み、アプリのコードは方式を意識しない
- サービスアカウントにドメイン全体の委任を設定し、自分のユーザーになりかわって Drive・Calendar を使う(Drive のフォルダやカレンダーをサービスアカウントに共有しなくてよい)
- 委任するスコープは必要なものだけにする(Calendar の読み取り、Drive のファイル操作)

## 5. 認証(OIDC)

- 任意の OIDC プロバイダーを使えるようにする。issuer URL・client ID は環境変数で設定
- クライアント認証は 2 方式から選ぶ
  - `client_secret`(client_secret_basic / post)
  - Workload Identity Federation: Kubernetes の ServiceAccount トークンを client assertion として送る(`private_key_jwt` 相当、RFC 7523)。IdP が対応している場合だけ使う
- ログインできるユーザーは 1 人。許可する `sub` または `email` を環境変数で指定し、それ以外は拒否する
- 権限管理(ロール)は持たない

## 6. 非機能

- DB: SQLite と PostgreSQL の両方で動くようにする。Drizzle ORM で差を吸収し、どちらを使うかは環境変数で選ぶ。SQLite のときは Kubernetes では PVC に置き、レプリカは 1
- DB に依存するテストは SQLite と PostgreSQL の両方で流す(PostgreSQL は Testcontainers など)
- バックアップ: SQLite はファイルを、PostgreSQL は `pg_dump` を定期的に取る(Drive に置くのも候補)
- 秘密情報(solidtime のトークン、OIDC の client secret、サービスアカウントの JSON キー)は環境変数か Kubernetes Secret で渡す。DB には保存しない
- 外部 API の失敗で画面全体が止まらないこと

## 7. 技術スタック(提案)

- TypeScript、React(Forma デザインシステムを使うため)
- フロント: Vite + React。API: Hono。定期実行の同期処理も API 側に置く
- DB アクセス: Drizzle ORM(SQLite / PostgreSQL)
- Google API: `googleapis`(認証は Application Default Credentials)
- OIDC: `openid-client`
- テスト: Vitest(ドメイン・ユースケース)、MSW(外部 API のモック)、Playwright(E2E)
- UI 実装に入るときに `forma-design-system` スキルを読み込む

## 8. TDD の進め方

1. ドメインの純粋な関数から始める: 稼働時間の集計 → 請求時間と金額 → 消費税 → 入金予定日 → 曜日別平均 → 不在の反映 → 予測のもとの選び方 → 着地見込み → 目安時間の警告 → 請求書ガイド(上の表の順)。今日の日付は引数で渡し、テストで固定できるようにする
2. ユースケース層: 「月次の請求見込みを作る」などを、外部サービスのフェイク実装で書く
3. アダプター層: 各 API の実レスポンスを記録したフィクスチャと MSW でテストする。テストでは実 API を呼ばない
4. E2E: ログイン → 案件登録 → 同期 → 請求書ガイド表示 の一連の流れを Playwright で確かめる

## 9. 決定事項と要調査

### 決定事項

- 割り切れない時間: 小数第二位で切り捨てた請求時間を数量にし、金額 = 数量 × 単価
- 日・月をまたぐ打刻: solidtime の集計どおり(開始日の側)
- 新しい案件の予測: 同じ取引先の実績 → なければ自分の稼働の空き
- 勤務時間帯は決めない。Out of Office がなければ祝日も含めて稼働できる日
- 構成: Vite + React + Hono
- DB: SQLite と PostgreSQL の両方
- Google: Workspace のサービスアカウント(ドメイン全体の委任)。WIF を使い、使えない環境では JSON キー
- 予測の初期値: 直近 8 週、3 か月先まで

### 要調査

なし(solidtime の単価の単位も確認済み)
